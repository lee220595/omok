# 렌주 구현·비교 검증 기록

검증일 2026-10-23. 시작 시 작업 폴더는 깨끗했고 `main`·`origin/main`·`origin/codex/state-model`이 모두 상태 모델 최종 커밋 `c51a17bc787eb7c7fa2cd01fc95cef9c928f778c`였다. fetch 후 확인했으며 기존 상태 구현은 원격 푸시·main 반영이 완료되어 있었다. 이번 작업은 `codex/renju-rules`에서 진행했다. 최종 커밋과 푸시 상태는 완료 보고·Git 원격 조회로 확인한다.

## 기준과 구현

[판정 계약](rules-spec.md)·[사례 명세](renju-cases.md)를 따른다. RIF 1996 제정/1998 정정 규칙과 Gomocup 일반 렌주 수정 정책을 근거로 삼았다. 비교 심판은 공식 조직의 GomocupJudge 커밋 `56cfd7dc1a0d1ec06d29f44a26931f375ad05991`이다. 최종 참가 연도·리그는 선정하지 않았다.

`omok_rules`는 GUI/Windows와 독립된 C++20 정적 라이브러리다. 구조 검사와 순수 보드 분석, 일반 대국의 상태/200수 정책 어댑터를 분리했다. 흑 정확한 5·장목·사사·재귀 예외 포함 삼삼, 백 5 이상, 만판·200수, 사/삼 집합 중복 제거를 구현했다. 결과를 상태에 자동 적용하거나 반칙패를 처리하지 않는다.

상태 소스·기존 테스트·GUI 소스·빌드 스크립트는 변경하지 않았다. 전체 상태 보존·종료 후 변경 거부·최대 225칸 이력·색 미배정 결과 기록을 재검토했으며 실제 결함이나 규칙 구현 차단 문제는 발견하지 않았다. 과거 문서의 규칙 미구현 표시는 당시 기록으로 구분하고 현재 문서는 갱신했다. 읽도록 지정된 문서와 참조 문서는 모두 존재했다.

## 실제 빌드·CTest

현재 Windows x64 호스트, GCC 13.3.0·MinGW-w64 11.0.1·CMake 3.29.3·Ninja 1.12.1 사용. 프로젝트 루트에서 실행했다.

```powershell
$aliasParent = Join-Path $env:TEMP 'omok-rules-build'
New-Item -ItemType Directory -Force $aliasParent | Out-Null
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build.ps1 -AliasParent $aliasParent
ctest --test-dir .\build\native-release --output-on-failure --no-tests=error
```

최종 빌드·링크·install 모두 종료 코드 0, 출력 컴파일 경고 없음. 기본 GUI exe도 함께 빌드·스테이징했다. 최종 CTest **52/52 통과, 실패 0**: 기존 상태 13개, 규칙 39개(35개 배치 × 8개 대칭/회전, 구조·상태 어댑터·수순 경계·만판 추가 그룹 4개). CHECK는 Release에서도 실행된다. 각 배치의 원본 보드 보존, 상태 어댑터의 전체 상태 보존도 검사했다. 만판 패턴은 마지막 빈칸을 225개 모든 위치로 바꾸어 검사했다.

최초 기존 테스트 시도는 과거 TEMP 별칭 경로의 실행 파일을 찾지 못해 **13개 Not Run**이었다. 기본 빌드 명령도 기존 별칭의 대상 불일치를 검출해 중단했다. 스크립트가 아무것도 삭제하지 않았으며 해당 연결을 보존하고 위의 별도 AliasParent로 복구했다. 복구 후 **구현 전 상태 테스트 13/13**을 먼저 통과했다. 한글 경로 우회 스크립트 자체는 유지했다.

중간 45개 CTest 실행에서는 같은 방향 사사·장목 완성 제외 사례 두 개와 이를 포함하는 상태 어댑터가 실패했다. 의도한 초기 배열과 다른 좌표를 입력한 것이 원인이었다. `XXX.X.XXX` 배치를 바로잡고, 어느 끝으로 채워도 장목이 되는 배치의 빠진 흑을 추가했다. 기대 판정이나 알고리즘을 실패에 맞추어 바꾸지 않았고 최종 사례를 공식 정의·실제 심판과 대조했다. 중간 실패를 최종 성공 기록과 혼동하지 않는다.

## 실제 비교 심판 실행

Python **3.13.7**, 표준 라이브러리만 사용했다. 원본 파일을 별도 새 캐시에 다운로드하고 SHA-256을 검증하는 경로도 실제 실행했다.

```powershell
python .\scripts\compare_rules.py --fetch --cache .\build\research\pinned-referee-verify --summary .\docs\verification\rules-comparison-summary.json
```

결과(종료 코드 0):

```text
2264 board comparisons; 6 play-loop boundaries; 0 mismatches
```

- 35개 고정 배치 중 구조 오류 2개는 심판에 전달하지 않았다. 나머지 33개 × 8변환 = **264개**를 대조했다. 원본 심판은 음수 좌표 등 구조 검사를 충분히 하지 않으므로 이를 제품의 허용 동작으로 가져오지 않는다.
- 고정 seed `20261023`의 임의 국소 배치 **1,000개**와 중앙 위협 밀집 배치 **1,000개**를 추가 대조했다. 합법 대국에서 도달 가능한 수순만 생성한 검사는 아니다.
- `check_forbid.py`를 원본 그대로 로드하고, `ai_match.py`의 원본 `__init__`·`make_move`·`play` 메서드를 AST로 선택해 변경 없이 컴파일·실행했다. 의존 모듈/프로세스는 로드하지 않았고 `next_move`만 고정 좌표 반환으로 대체했다.
- 보드 비교는 원본 `make_move`의 정상 0/금수 -2/승리 1 결과와 비교했다. 세부 금수 사유는 이 인터페이스에서 구분하지 않으므로 자체 Reason까지 심판과 일치한다고 주장하지 않는다.
- 원본 `play` 루프에 준비 배치 길이 198·199·200과 두 가지 보드(승리 없는 패턴/백 승리 준비)를 넣어 **6개** 경계를 실행했다. 다음 착수 요청 수는 각각 2·1·0이다. 준비 배치 199개 후 백의 200번째 승리는 백 승리이며, 200개 후에는 다음 착수를 요청하지 않는다. 심판 로그를 요약 파일에 기록했다.

고정 소스 해시:

| 파일 | SHA-256 |
|---|---|
| check_forbid.py | `784f5bf1c0d715078474adb89903cc62be443bc739376e1f2b371ed95f2d368b` |
| ai_match.py | `93831daa81fcbcd40f4c6e87156589c6f49c5650063e5d6d7a6198e268bbe815` |

추적하는 [요약 JSON](verification/rules-comparison-summary.json)은 입력 fixture 해시·각 기본 사례의 실제 입력/출력·6개 경계 출력·Python 버전·전체 로그 해시를 포함한다. 전체 2,264개 입력/출력은 재현 명령이 `build/research/rules-comparison.json`에 생성한다. 캐시·전체 생성 로그·원본 외부 소스는 Git과 제품 배포에서 제외한다. `--fetch`는 누락 파일만 내려받으며 해시가 다른 기존 파일을 덮어쓰지 않는다. 네트워크가 없는 곳은 동일 해시의 파일을 캐시에 제공하고 `--fetch` 없이 실행한다. 비교 도구는 불일치나 실행 실패 시 성공 종료하지 않는다.

`check_forbid.py`의 GPL-3.0-or-later 표기를 확인했다. 원본을 제품 코드에 복사·번역하거나 배포하지 않았다. 저장소 전체의 통일 라이선스와 다른 매니저 기능의 재배포 조건을 확인한 것으로 확대하지 않는다.

## 미검증·제약·다음 단계

- **자체 테스트 통과**, **심판 소스 조사**, **위 범위의 실제 원본 함수/루프 실행**을 수행했다. 전체 GomocupJudge client/server·실제 AI 엔진·프로토콜·프로세스·시간/자원 제한은 실행하지 않았다. 통신 규격 호환·공식 대회 규칙 전체 일치·매니저 채택 완료로 표시하지 않는다.
- 확인한 사례의 불일치는 0이며 구현을 막는 규칙 해석 충돌은 발견하지 않았다. 임의의 모든 배치·모든 재귀 깊이에 대한 완전 일치 증명과 최악 성능 검증은 하지 않았다. 전체 225점 금수 힌트의 GUI 반응성은 GUI 단계에서 측정해야 한다.
- MSVC·비Windows·개발 도구 없는 별도 Windows 10/11 PC·메모리 sanitizer 환경이 없어 실행하지 않았다. 상태·규칙 소스가 Windows API를 사용하지 않는 것과 다른 OS 빌드 검증을 구분한다.
- GUI 코드는 변경하지 않았고 전체 빌드는 성공했다. 이번에 GUI를 직접 띄워 표시·닫기를 재검증하지 않았다. 과거 GUI 실행 기록은 [상태 검증](verification-state.md)에 있다. ZIP도 새로 만들지 않았다.
- 규칙 판정의 실제 상태 적용·오프닝·실대국·기보·AI는 이번 범위 밖이다. 다음은 출처와 사용 조건이 확인된 준비 배치를 순서대로 복원하는 오프닝 계층이다. 현재 모듈·명세·회귀 검증은 그 단계에 필요한 기반을 제공한다. 최종 참가 연도·리그·운영 심판 버전 선정과 실제 엔진/매니저 연동 검증은 별도로 남는다.
