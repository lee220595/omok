## 3. 상태 API의 핵심 계약

- 좌표는 `Coordinate{row, column}`, 왼쪽 위 `(0,0)`, 행은 아래·열은 오른쪽, 범위 0~14. 인덱스는 `row * 15 + column`, 범위 0~224. 잘못된 좌표의 조회는 nullopt이며 빈칸과 구분한다.
- 기본 생성은 빈 보드·빈 이력·색 미배정·다음 흑·InProgress다. 실제 대회 오프닝·A의 흑 배정을 정한 것은 아니다.
- Participant, StoneColor, Cell, RelativeStone은 별도 타입이다. enum 정수 값을 프로토콜 값으로 송신하지 않는다. 상대 관점 변환은 의미 매핑만 있으며 송수신은 없다.
- 실제 배치 참가자와 현재 색 소유자는 별개다. 색 재배정은 돌·이력·다음 색을 바꾸지 않으며 다음 참가자·자신/상대만 다시 계산한다.
- `commit_placement(placement, next_color)`는 검증된 배치의 저장 트랜잭션이다. 상태는 범위·점유·enum·현재 예정 색·종료 여부를 검사하고 실패 시 **전체 상태를 보존**한다. 다음 색은 호출자가 명시하며 자동 교대하지 않는다.
- 상위 대국/오프닝 제어가 입력 참가자의 권한·단계·돌 수·다음 색을 정하고 규칙 모듈이 합법성/종료를 판정해야 한다. 배치 참가자가 색 소유자와 다르거나 같은 색이 이어지는 기록을 상태가 저장할 수 있다는 사실을 일반 대국 규칙으로 해석하지 않는다. GUI/AI를 상태 API에 직접 연결하지 않는다.
- `finish`는 외부에서 결정한 Won{승자 A/B}, Draw, Aborted를 기록한다. 선·금수·수순·시간을 검사하지 않는다. 종료 후 다음 차례가 없고 변경은 reset 전까지 거부한다.
- `reset`은 보드·이력·배정·차례·결과 전체를 초기화한다. 잘못된 설정이면 기존 상태 그대로다. 고정 배열 보드·최대 225개 이력은 동적 할당 없이 소유한다. 읽기 전용 span은 스냅샷이 아니므로 보관하려면 복사한다.
- 화면 픽셀/표시 레이블은 GUI, 프로토콜 x/y는 AI 어댑터가 상태의 열/행으로 변환한다. 이번에 구현한 변환은 상태 좌표↔선형 인덱스뿐이다.

## 4. 선택 기술과 이유

C++20·Win32 User32/GDI32·CMake 3.24+·MinGW-w64 x64/Ninja를 유지했다. Windows 전용 GUI를 추가 런타임 없이 배포하고 도메인 코드는 독립시키려는 선택이다. 설치된 검증 도구는 GCC 13.3.0, MinGW-w64 11.0.1, CMake 3.29.3, Ninja 1.12.1이다.

상태는 표준 C++만 사용하며 테스트 실행 파일도 GUI와 링크하지 않는다. 별도 프레임워크 대신 작은 CHECK 실행기를 CTest에 등록해 다운로드·새 라이선스 없이 Release 검증을 수행한다. GCC 런타임은 실행 파일에 정적 링크한다. 라이선스 원문·외부 고지는 기존과 동일하고 자체 코드 공개 라이선스는 아직 미선정이다. 루트 빌드는 기존 Windows x64 전용이며 비Windows 실행을 검증한 것은 아니다.

## 5. 실제 실행 명령·결과

프로젝트 루트에서 이번에 실제 실행했다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build.ps1
ctest --test-dir .\build\native-release --output-on-failure --no-tests=error
```

빌드·링크·install 성공(종료 코드 0), 출력 컴파일 경고 없음. CTest는 **13/13 통과, 실패 0**이었다. 전체 좌표 225개 왕복, 경계, 거부 시 전체 상태 보존, 두 색 배정과 관점, 색 변경 후 이력/차례 일관성, 종료 기록·초기화, 자동 판정 부재를 검증했다. 상세 사례명은 [검증 기록](verification-state.md)에 있다. BUILD_TESTING은 기본 켬이며 CTest는 빌드와 별도로 실행한다.

```powershell
& 'C:\Program Files\mingw64\bin\objdump.exe' -p build\native-release\bin\omok_state_tests.exe |
    Select-String 'DLL Name|Magic|Subsystem'
```

테스트 exe는 PE32+ x64 콘솔이며 KERNEL32.dll·msvcrt.dll만 참조했다. 기본 GUI도 새 빌드의 dist/omok/omok.exe를 computer-use로 실행해 제목·한글 안내(보이는 부분)를 확인하고 닫기 단추 후 창이 사라짐을 확인했다. GUI 프로세스 종료 코드는 수집하지 않았다. 일부 화면은 다른 앱에 가려져 전체 화면 검증으로 과장하지 않는다.

기존 빌드 스크립트·src/gui·src/app은 무변경이다. 최초 기반 검증·패키징의 상세 기록은 [과거 기반 검증](verification-foundation.md)에 보존했다. 이번에는 ZIP을 재생성하지 않았으며 기존 ZIP과 과거 해시를 새 상태 구현의 산출물로 소개하지 않는다. 테스트 실행 파일은 GUI 배포 폴더에 install하지 않는다. build/dist는 Git에 없으므로 clone 후 빌드해야 한다.

## 6. 미검증·이유·알려진 문제

- 렌주·오프닝·실대국·프로토콜·모의 AI는 이번 범위 밖이고 해당 모듈이 미구현이므로 테스트하지 않았다. `state.no_adjudication`은 판정의 정확성이 아니라 판정 책임이 상태에 섞이지 않았음을 확인한다.
- 별도 개발 도구 없는 Windows 10·11 PC/VM·MSVC·비Windows 환경이 없어 실행하지 않았다. DLL 목록만으로 클린 환경 완료를 보장하지 않는다.
- DPI/복수 모니터·최대화·장시간 GDI·오류 대화상자·메모리/경쟁 검사·스레드 안전성은 검증하지 않았다. 현재 상태 객체는 단일 작성자 계약이다.
- Ninja/windres의 한글·공백 경로 문제는 기존 ASCII junction·상대 리소스 컴파일·Ninja 메타데이터 정리로 우회한다. 경로 우회를 임의 제거하지 않는다. TEMP에 한글이 있으면 기존 ASCII 경로를 AliasParent로 지정한다.
- 재빌드 전 실행 중인 창을 닫는다. Windows 파일 잠금으로 링크가 실패할 수 있으며 빌드 스크립트는 앱을 강제 종료하지 않는다.
- 목표 대회 연도·리그는 추후 선정한다. 잠정 15×15 렌주·준비 오프닝·패스 금지·200수 무승부·30초/180초·엔진 메모리 1GB·한 CPU 코어·pondering 금지는 문서 기준일 뿐 아직 코드에 적용된 대국 설정이 아니다.
- 준비 오프닝 수순 계산·200번째 수 우선순위·흑 동시 5목/금수·재귀적 삼삼·초기화 계측·AI 오류 결과·자원 강제는 대상 심판과 대조해야 한다. 결과 사유·전체 대국 이벤트 이력은 향후 규칙·대국 제어·기보에서 구체화한다.
- Piskvork·GomocupJudge·Rapfi·Pela는 기존 소스/문서 조사만 있고 실제 실행·연동은 미검증이다. 매니저 선정·GUI 연결·버전/모델 재배포 조건이 남아 있다. GomocupJudge의 명시적 라이선스는 미확인이다.
- 온라인·무르기·연습용 제한 완화는 범위 밖이며 Swap2 GUI 입력 방식은 보류다. 기존 Swap2 후 렌주 결합을 기본값으로 되살리지 않는다.

## 7. 다음 작업과 완료 기준

1. 최신 Git/AGENTS/사용자 지시 확인 후 다음 범위를 진행한다. 상태 구현 승인을 렌주·AI 구현 전체 승인으로 확대하지 않는다.
2. 다음 규칙 단계는 공식 기준·대상 심판을 고정하고 가짜 삼·재귀 예외·동시 5목·장목·사사·200수 경계의 사례 명세부터 작성한다. 구조적 상태 오류와 게임 반칙/종료를 분리한다. 이후 승인된 규칙 구현과 자동 회귀 검증을 추가한다.
3. 오프닝·대국 제어는 상태 API 앞에서 입력 권한·다중 배치·다음 색을 관리하도록 설계한다. A/B·흑/백·자신/상대와 실제 배치 참가자의 매핑을 유지한다. 종료 사유와 전체 오프닝 선택 이력은 현재 Placement 기록만으로 완성됐다고 보지 않는다.
4. 이후 준비 오프닝/Swap2 → 사람 대 사람 GUI → 모의 AI 오류 주입·비동기 외부 AI → 실제 엔진/매니저 대조 → 기보/관전 → 클린 환경 배포 순서를 따른다. 자체 AI 알고리즘은 게임·외부 AI 검증 후 별도 단계다.
5. 판정 충돌 시 중단·로그·결과 미확정, 대회 오류 정책·별도 재시도 제외 등 승인 사항을 유지한다. 테스트 없는 기능을 완료로 보고하지 않는다.
6. 일반 작업은 main, 큰 변경·실험은 codex/<작업명>으로 검증·커밋·일반 푸시한다. 원격은 origin=https://github.com/lee220595/omok.git. 기존 이력·다른 작업을 보존하고 비밀정보·생성물은 제외한다. 완료 보고에 커밋·브랜치·푸시·실제 검증·미검증을 남긴다.
