# 게임 상태 모델 계약

2026-10-19 상태 모델·관련 자동 테스트 구현 승인 반영. 공개 헤더는 `src/state/include/omok/state/game_state.hpp`, 구현은 `src/state/game_state.cpp`다. `omok_state`는 C++20 표준 라이브러리만 사용하는 정적 라이브러리이며 GUI·Windows API·프로토콜에 의존하지 않는다.

## 좌표와 보드

- `Coordinate{row, column}`의 원점은 **왼쪽 위 교차점**이다. 행은 아래로, 열은 오른쪽으로 증가한다. 둘 다 0~14, 크기는 항상 15×15다.
- 선형 인덱스는 `row * 15 + column`이며 0~224다. `(0,14) → 14`, `(14,0) → 210`, `(14,14) → 224`. 행·열을 x·y로 해석해 서로 바꾸지 않는다.
- 원시 입력을 담을 수 있게 Coordinate 자체는 잘못된 정수도 표현한다. `is_on_board()`·`index()`가 검사하며 범위 확인 전에 곱셈·배열 접근을 하지 않는다. 음수·INT_MIN·INT_MAX도 거부한다. `from_index()`는 225 이상을 거부한다.
- `cell_at()`은 범위 밖이면 `nullopt`, 유효한 빈 교차점이면 `Cell::Empty`를 반환한다. 잘못된 좌표와 빈칸을 같은 값으로 처리하지 않는다.
- 보드·이력 접근은 읽기 전용 span이다. 데이터는 상태 객체가 소유하고 외부에 가변 참조를 주지 않는다. span은 복사본이 아니므로 이전 상태를 보관하려면 상태 또는 필요한 데이터를 복사한다. 값 복사한 GameState는 보드·이력을 공유하지 않는다.

### 이후 변환 경계

| 경계 | 향후 담당 책임 | 현재 구현 |
|---|---|---|
| 화면 픽셀·표시 레이블 → 상태 | GUI가 교차점 선택·여백·픽셀 반올림·표시 원점/번호를 변환하고 유효성을 확인 | 미구현 |
| 상태 → 화면 | GUI가 행·열을 화면 위치로 투영. 표시 방식 변경으로 보드 저장 순서를 바꾸지 않음 | 미구현 |
| 프로토콜 좌표 → 상태 | AI 어댑터가 형식·범위를 검증해 x를 열, y를 행에 대응. 상태 모듈은 다시 범위를 검사 | 미구현 |
| 상태 돌 → 자신/상대 → 프로토콜 | 색 대응을 읽어 의미를 구한 뒤 어댑터가 프로토콜 값을 인코딩 | 의미 매핑만 구현, 송수신·숫자 인코딩 미구현 |

상태 API에는 화면 픽셀, 1부터 시작하는 표시 번호, CSV/문자열, Gomocup 명령을 넣지 않는다. 실제 GUI의 표시 번호·원점이나 오프닝 선택 흐름을 이 문서가 추가로 확정하지 않는다.

## 참가자·색·자신/상대 분리

- `Participant::A/B`: 대국 참가자 식별자. 사람·AI 종류나 이름은 이후 대국 설정에서 관리한다.
- `StoneColor::Black/White`: 돌 색. 빈칸은 돌 색이 아니며 `Cell::Empty/Black/White`로 표현한다.
- `ColorAssignment`: 흑 소유자 하나만 저장해 A/B의 중복 배정을 방지한다. 백은 다른 참가자로 유도한다. 초기에는 두 색 모두 미배정이다.
- `RelativeStone::Own/Opponent`: 특정 참가자의 관점. Gomocup의 숫자 값이 아니며 enum을 정수로 캐스팅해 송신하지 않는다. `colors().relative_to(color, observer)`는 색 미배정·잘못된 인자에 `nullopt`를 반환한다. 빈칸은 이 함수의 돌 색 인자로 넘길 수 없다.
- `Placement::placed_by`는 **그때 실제 배치한 참가자**, `color`는 배치된 돌의 실제 색이다. 현재 색 소유자와 다른 개념이다. 색을 재배정해도 기존 보드·착수 이력·다음 돌 색은 바뀌지 않는다. 다음 참가자와 자신/상대 해석만 새 배정으로 계산된다.

## 초기 상태와 API 책임

기본 생성 상태는 빈 보드·빈 이력·색 미배정·다음 돌 흑·결과 `InProgress`다. 이것은 저장 객체의 초기값이며 실제 대회 오프닝이나 참가자 A가 흑이라는 결정을 뜻하지 않는다. 대국 제어/오프닝 모듈이 첫 요청 전에 필요한 배정과 다음 색을 공급해야 한다.

| API | 하는 일 | 하지 않는 일 |
|---|---|---|
| `reset(InitialState = {})` | 보드·이력·결과·색 배정·다음 색 전체 초기화. 설정의 잘못된 enum 값은 거부 | 기보 가져오기, 프로세스 정리, GUI 재시작 |
| `assign_colors(black_owner)` | 유효한 흑 소유자 배정/재배정. 백 소유자 유도 | 색 선택 권한·Swap2 단계 확인, 기존 돌·이력 색 바꾸기 |
| `commit_placement(placement, next_color)` | 범위·빈칸·enum·예정된 돌 색·진행 중 여부를 검사한 뒤 보드·이력·다음 색을 한 번에 갱신 | 입력 참가자의 착수 권한, 금수·승리·오프닝 제약, 자동 교대 |
| `finish(result)` | 외부에서 결정한 `Won{winner}`·`Draw`·`Aborted` 기록. 다음 색·참가자는 없음으로 전환 | 승리·반칙·시간 초과·200수·만판의 자동 판정 |

### 착수 트랜잭션의 전제

`commit_placement`는 최종 사용자의 “착수 요청”을 그대로 받는 서비스가 아니라 **상위 모듈이 검증한 배치를 기록하는 API**다. 상위 모듈은 다음을 책임진다.

1. 현재 입력을 요청받은 참가자인지 확인한다. 일반 대국은 `next_participant()`를 사용할 수 있지만 색 미배정 때에는 `nullopt`이므로 오프닝 제어가 입력 주체를 관리한다.
2. 규칙 모듈의 합법성·종료 판정과 오프닝 단계·돌 수 제한을 적용한다.
3. 실제 배치 참가자·색과 **다음 돌 색을 명시**해 전달한다. 상태는 배치 색과 현재 `next_color()` 일치를 확인하지만 자동으로 교대시키지 않는다. 여러 돌 배치·추가 배치 흐름 자체는 아직 구현하지 않았다.

따라서 A가 백 돌을 배치하거나 같은 색을 다음에도 지정하는 기록은 저장 구조상 허용될 수 있다. 이것을 일반 대국의 착수 허용 규칙으로 해석하지 않는다. 실제 GUI·AI 입력은 향후 대국 제어를 거쳐야 하며 상태 API를 직접 연결하지 않는다. 이 구분은 추후 준비 오프닝·Swap2의 배치 참가자와 색 소유자를 혼동하지 않기 위한 것이다.

### 원자성·이력·결과

- 모든 유효성 검사는 쓰기 전에 수행한다. 실패 시 보드·이력·색 배정·다음 차례·결과 전체가 그대로다. 거부 요청을 이력에 넣지 않는다.
- 이력은 최대 225개의 고정 배열이다. 빈 교차점에만 기록하므로 보드 점유 수와 이력 길이가 일치한다. 배열 순서가 착수 순서이며 `인덱스 + 1`이 기록 번호다. 별도 동적 할당이 없어 기록 도중 할당 실패로 일부 필드만 갱신되는 경로가 없다.
- `InProgress`, `Won{Participant}`, `Draw`, `Aborted`는 variant로 분리한다. 무승부/중단에 승자를 넣는 모양을 표현하지 않는다. `finish(InProgress{})`나 잘못된 승자 enum은 거부한다. 결과 사유·판정 근거는 향후 규칙·대국 제어에서 구체화할 항목이다.
- 종료 후 추가 배치·색 재배정·중복 종료는 `AlreadyFinished`로 거부한다. 다시 사용할 때는 명시적으로 reset한다. 잘못된 reset 설정도 이전 상태를 보존한다.
- `StateError`는 저장 유효성 오류다. 렌주 반칙패·AI 패배 등 대국 결과나 제재로 자동 변환하지 않는다. 복수 오류의 반환 우선순위는 제품 규칙으로 고정하지 않는다.
- 5목·장목·200수·만판에서도 자동으로 종료하지 않는다. 다음 색이 남아 있어도 합법 수가 존재함을 보장하는 것은 아니다. 이 정책은 `state.no_adjudication`으로 검증한다.
- 스레드 동기화는 제공하지 않는다. 향후 대국 제어가 단일 작성자/동기화를 보장하고 비동기 GUI·AI 전달에는 복사 스냅샷 또는 명시적 수명 관리를 사용한다.

## 자동 테스트

외부 프레임워크·다운로드 없이 테스트 실행 파일을 CTest에 13개 사례로 등록했다. Release에서도 실행되는 CHECK를 사용하며 `assert`/NDEBUG에 의존하지 않는다. 결과·실제 명령·미검증 범위는 [상태 모델 검증 기록](verification-state.md)을 따른다.
